# codyssey_all_E1_3

# Mini NPU Simulator

2차원 패턴과 필터의 MAC 점수를 계산하여 패턴을 판별하는
Python 콘솔 프로그램입니다.

## 실행 방법

- Python 3.8 이상이 필요합니다.
- 외부 라이브러리는 사용하지 않습니다.
- main.py와 같은 폴더에 공식 data.json을 둡니다.

```powershell
python main.py
```

- 1번: 3×3 필터 A, B와 패턴을 직접 입력합니다.
- 2번: data.json의 패턴을 일괄 분석합니다.

## 파일 구조

```text
codyssey_all_E1_3/
│
├── main.py              # 프로그램 시작 및 모드 선택
├── data.json            # 크기별 필터와 테스트 패턴
├── README.md            # 실행 안내 및 결과 분석
│
└── src/
    ├── __init__.py      # 패키지 초기화 파일
    ├── matrix.py        # 2차원 배열 및 십자가 패턴 생성
    ├── mac.py           # 반복문 기반 MAC 연산
    ├── judge.py         # 라벨 정규화 및 허용오차 기반 판정
    ├── mode_input.py    # 3×3 사용자 입력 및 검증
    ├── mode_json.py     # JSON 검증, 일괄 판정 및 결과 요약
    └── perf.py          # MAC 실행 시간 측정 및 성능 표 출력
```

## 구현 요약

- 패턴과 필터는 2차원 리스트로 저장합니다.
- MAC은 같은 위치의 값을 곱하고 누적하는 이중 반복문입니다.
- 라벨 +와 cross는 Cross로, x는 X로 정규화합니다.
- 두 점수의 차이가 1e-9보다 작으면 UNDECIDED로 판정합니다.
- JSON의 키, 배열 크기, 숫자 값, 라벨을 검증합니다.
- 잘못된 케이스는 FAIL로 기록하고 다음 케이스를 처리합니다.
- MAC 호출 구간을 10회 측정한 평균 시간을 출력합니다.

### [실패 원인 분석]

1. 실제 실행 결과는 전체 [6]건, 통과 [3]건, 실패 [3]건이었다.
2. expected와 필터 키는 비교 전에 Cross 또는 X로 정규화했다.
3. 정규화를 통해 +와 Cross가 다른 문자열이어서 발생하는 실패를 방지했다.
4. 패턴과 필터의 크기를 검사하여 잘못된 인덱스 접근을 방지했다.
5. 스키마 오류는 해당 케이스의 FAIL로 기록하고 다음 케이스를 처리했다.
6. 실수 누적 계산에서는 표현 오차로 아주 작은 점수 차이가 생길 수 있다.
7. 점수 차이가 1e-9보다 작으면 UNDECIDED로 처리했다.
8. UNDECIDED는 expected의 Cross 또는 X와 다르므로 FAIL이 된다.
9. 동점 FAIL은 판정 정책에 따른 결과이며 반드시 구현 결함을 뜻하지 않는다.
10. size_5_1은 Cross 점수 0.9, X 점수 0.8999999999999999로, 차이가 1e-9보다 작아 UNDECIDED로 판정되었다. expected는 X이므로 FAIL이다.
11. size_13_2는 Cross 점수 7.499999999999997, X 점수 7.5로, 차이가 1e-9보다 작아 UNDECIDED로 판정되었다. expected는 Cross이므로 FAIL이다.
12. size_25_1은 Cross 점수 4.9, X 점수 4.899999999999999로, 차이가 1e-9보다 작아 UNDECIDED로 판정되었다. expected는 X이므로 FAIL이다.
13. 세 케이스는 부동소수점 표현 오차로 미세한 점수 차이가 있지만, 허용오차 정책에 따라 동점으로 처리되었다. 따라서 이번 FAIL은 구현 오류가 아니라 동점 판정과 expected의 불일치에 따른 결과이다.
14. 예상 라벨과 판정이 다르면 입력 데이터와 필터를 먼저 확인한다.
15. 이후 MAC 계산과 판정 로직을 확인하여 원인을 구분한다.

### [시간 복잡도 분석]

| 크기 | 평균 시간(ms) | MAC 횟수(N²) |
|---|---:|---:|
| 3×3 | 0.002310 | 9 |
| 5×5 | 0.004650 | 25 |
| 13×13 | 0.021790 | 169 |
| 25×25 | 0.074250 | 625 |

각 시간은 MAC 함수 호출을 10회 측정한 평균이다.

입력, 출력, 파일 읽기, 배열 생성은 측정 구간에서 제외했다.

N×N 배열의 모든 칸에서 곱셈과 누적을 수행하므로 시간 복잡도는 O(N²)이다.

필터 두 개로 판정하면 2N²번 수행하지만 시간 복잡도는 O(N²)이다.

위 표의 MAC 횟수는 필터 한 개를 기준으로 한다.

실측 시간은 함수 호출과 시간 측정 비용, 실행 환경의 영향을 받는다.

따라서 측정 시간의 비율이 N²의 비율과 정확히 같을 필요는 없다.

실제 측정 결과에서 관찰한 경향은 다음과 같다: 배열 크기가 3×3에서 25×25로 커질수록 평균 MAC 연산 시간이 증가했다. 이는 처리해야 할 원소 수가 N²에 따라 증가하는 것과 일치하는 경향이다. 다만 함수 호출 비용과 측정 오차 때문에 시간 증가 비율이 N² 비율과 정확히 같지는 않았다.


### [대규모 입력(1000×1000)의 예상 병목과 최적화 전략]

1000×1000 배열에서는 필터 한 개당 1,000,000회의 MAC이 필요하며,
필터 두 개로 판정하면 총 2,000,000회의 MAC을 수행한다.
시간 복잡도는 O(N²)이며, 현재 Python 이중 반복문에서는
반복문 실행과 리스트 인덱싱, 숫자 객체 처리 비용도 누적된다.
기존의 25×25 측정만으로 1000×1000 실행 시간을 정확히 예측할 수는 없다.

메모리 사용량 역시 배열 원소 수에 따라 O(N²)로 증가한다.
패턴 한 개와 필터 두 개를 모두 저장하면 총 3,000,000개의 원소가 필요하다.
Python 리스트는 숫자 자체뿐 아니라 객체 참조와 리스트 관리 공간도 사용하므로,
메모리 사용량을 단순히 원소 수 × 8바이트로 계산할 수 없다.
JSON 로딩 과정에서도 문자열과 파싱된 배열이 함께 존재하면
최대 메모리 사용량이 커질 수 있다.

최적화는 다음 순서로 검토한다.

1. 실제 1000×1000 입력의 실행 시간과 최대 메모리 사용량을 측정해 병목을 확인한다.
2. 반복문 안에서 행을 지역 변수로 저장하여 중복 인덱싱을 줄인다.
3. 같은 패턴으로 두 필터의 점수를 한 번의 순회에서 계산하는 방식을 비교한다.
   곱셈 횟수는 같지만 패턴 접근과 반복문 실행 비용을 줄일 가능성이 있다.
4. 1차원 배열로 변환하여 중첩 인덱싱을 줄이는 방법을 비교한다.
   단, 변환 시간과 원본·변환본을 함께 보관하는 메모리 비용도 확인한다.
   Python의 평탄화된 리스트도 숫자 객체 자체의 연속 배치를 보장하지는 않는다.
5. 메모리가 부족하면 데이터를 블록 단위로 읽고 부분 MAC 결과를 누적한다.
   다만 json.load()로 전체 파일을 읽은 뒤 블록으로 나누는 것만으로는
   파일 로딩 시 최대 메모리 사용량을 줄일 수 없다.
   실제 메모리 절감을 위해서는 블록별로 읽을 수 있는 파일 구조도 필요하다.
6. 루프 언롤링으로 반복 제어 비용을 줄이는 방법도 후보가 될 수 있다.
   그러나 Python에서는 코드가 복잡해지고 성능 개선이 보장되지 않으므로
   동일 입력과 반복 횟수로 측정한 뒤 적용 여부를 결정한다.

현재 MAC은 데이터를 한 번씩 순서대로 읽으므로,
블록화가 항상 캐시 효율이나 실행 시간을 개선하는 것은 아니다.
또한 누적 순서를 바꾸는 최적화는 부동소수점 결과에 영향을 줄 수 있으므로
점수와 epsilon 기반 판정이 유지되는지도 함께 검증해야 한다.
NumPy 등의 벡터화는 외부 라이브러리 사용 금지 조건 때문에
이번 과제에는 적용하지 않는다.

### CPU와 NPU의 처리 방식 및 병목 비교

현재 프로그램은 Python 반복문으로 MAC을 순서대로 수행한다.
CPU 자체는 SIMD와 여러 코어를 이용한 병렬 처리가 가능하지만,
현재 구현은 이러한 기능을 명시적으로 활용하지 않는다.
따라서 대규모 입력에서는 Python 실행 비용과 메모리 접근 비용이
주요 병목 후보가 된다.

각 위치의 곱셈은 서로 독립적이므로 여러 처리 단위에 나눌 수 있다.
각 처리 단위가 부분 합을 계산한 뒤 최종 합으로 합치는 방식으로
MAC을 병렬화할 수 있으며, Cross와 X 점수도 독립적으로 계산할 수 있다.
다만 작업 분배, 데이터 전달, 부분 합 결합에도 비용이 발생하므로
작은 입력에서는 병렬화의 이점이 작거나 오히려 느려질 수 있다.

NPU는 많은 MAC을 병렬로 처리하는 연산 장치를 갖추고 있다.
하지만 연산 장치에 데이터를 충분히 공급하지 못하면
연산 성능보다 메모리 대역폭과 데이터 이동이 병목이 된다.
특히 이번처럼 원소를 읽어 한 번씩 사용하는 MAC은 데이터 재사용이 적어,
연산이 빨라질수록 메모리에서 데이터를 가져오는 비용이 중요해질 수 있다.

반대로 여러 연산에서 같은 데이터를 재사용할 수 있고
데이터 공급이 충분하다면 연산 장치의 처리량이 병목이 될 수 있다.
따라서 CPU와 NPU의 성능 차이는 직렬·병렬 처리 여부뿐 아니라
데이터 재사용, 메모리 대역폭, 장치 간 전송 비용까지 함께 고려해야 한다.
현재 프로그램은 MAC의 계산 원리를 구현한 시뮬레이터이며,
실제 NPU의 병렬 실행이나 메모리 구조를 재현한 것은 아니다.
